# Mihomo 手动 Reality 节点卡顿排查

## 已确认的回归

本次以老仓库 `Angasky/mxioc-vpn-manager` 的 `main` 提交 `12d02f1` 为基线。用户反馈为 VLESS / Reality：Mihomo 直接使用原始配置正常，经总控订阅后上网卡顿。未连接生产服务器，未读取真实节点 UUID 或订阅链接。

代码排查发现三个参数传递问题：

1. `get_cached_config()` 从 `4393e5b` 起，对所有未声明该选项的 Reality 节点补上 `support-x25519mlkem768: true`。这发生在读取时，原始文件没有此选项也会在下载的 YAML 中出现，手动导入节点与总控创建节点没有区别处理。
2. `normalize_reality_options()` 在手动批量导入、校验时也补写 true。其他配置保存可能将之前自动补写的选项持久写入旧节点。
3. `node_to_uri()` 不传递这个布尔选项，`parse_node_link()` 不读取显式值；编辑界面重建 `reality-opts` 时也丢失其他高级字段。显式 false 可被丢失并重新变成 true。

这些路径会改变原节点的握手，而不是只管理节点列表。它们符合“原始配置正常、总控输出异常”的排查方向；生产链路的实际改善仍需更新订阅后对照确认，不能仅靠代码或本地抓取断言所有卡顿均来自同一个原因。

## 隔离 Mihomo 实测

使用 Mihomo v1.19.33、临时生成的测试公钥、回环监听端口和无效测试域名捕获真实 TLS ClientHello。没有连接生产入站，也没有将 TLS 连通当作 Reality 认证通过。

一次修复后完整测试的首条 TLS 记录大小为：

| 输入 | TLS 记录大小 | X25519MLKEM768 key share |
| --- | ---: | --- |
| 原配置未指定选项 | 601 字节 | 不携带 |
| 显式 false | 537 字节 | 不携带 |
| 显式 true | 1727 字节 | 携带，分组 0x11ec |

指纹内含随机数据，各轮大小会变化；本轮默认 / false 约为 0.5–0.6 KB，true 约为 1.7–1.8 KB。开启混合握手改变了 TLS key share 及首包大小，可能影响特定服务端、路径或中间设备的兼容性。该测试没有测量生产 MTU、重传率、运营商干扰或持续下载速度，也不表示启用此功能必然变慢；新版服务端可能需要它。

## 修复行为

- 读取现有 YAML、下载完整订阅与获取快照不再隐式开启新握手方式。
- 手动导入的原链接未声明该选项时，不替其指定 true 或 false；显式声明的值原样保留。
- 总控生成的 Reality 节点仍由 `remote_manager.inbound_nodes()` 明确设置兼容选项，并通过链接往返保留，不全局关闭新服务端需要的功能。
- VLESS 编辑增加“Reality 混合密钥握手（Mihomo）”选项。保存保留其他未展示的 Reality 参数；布尔类型由后端校验。
- 不连接所有服务器，不修改 UUID、端口、套餐、限速、流量倍率或已用量。SNI 42 域名、隔离探测及地址绑定流程保持原实现。

## 已有节点怎样处理

先安装本次代码，再在 Mihomo 更新订阅。若原文件本来没有该选项、只是下载时被程序补写，更新后即恢复原先的默认握手。

如果之前已通过导入或保存将 true 写进旧节点，程序无法判断它是自动添加还是用户明确选择，因此不会静默删掉。对照原始正常配置，在总控「节点管理 → 编辑 → Reality 混合密钥握手」选择“沿用客户端默认”，保存并刷新 Mihomo 订阅；若原配置明确为 false，则选择“关闭混合密钥握手”。建议先用一个旧节点验证，再处理其他同类节点。总控新建、确实需要混合握手的节点保留“启用”。不要为排查而更换 SNI、UUID、关闭证书验证或清空计费用量。

若更新后仍慢，用同一 Mihomo 版本、同一节点、同一目标及时间窗口比较原配置与总控订阅，重点查看连接错误、握手超时、重传、DNS 与业务策略实际选中的节点；不能只比较延迟测速数字。分享日志前移除 UUID、公钥之外的凭据、真实订阅地址、密码和客户端控制器密钥。
